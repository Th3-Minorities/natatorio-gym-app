\subsection{\revised{Performance Results and Documentation}}
On \texttt{main} at commit c6d596d (Nov 8), the backend workflow took 2 min 40 s and the frontend workflow 6 min 59 s, both passing. The load test ran k6 on Docker Desktop on a laptop with an Intel i7-1260P (12 cores), 15.7 GB of RAM, and Windows 11. Docker had 16 CPUs and 7.6 GB, and PHP-FPM ran with its default 5 workers. The database held 100 seeded members, and sign-in happened before the timed part. Each run reseeded the database. The team thresholds, which have no SRS number, are a Check In p95 under 3 seconds, errors under 1\%, and every check passing. The peak and stress sizes are a team decision: the peak is 50 Check Ins in 5 minutes (about a third of the 150 daily visits in the busiest hour, compressed), and the stress run doubles it. Table~\ref{tab:load} lists the results.

Occupancy starts at 3 because the seed already has 3 people inside. Peak and stress meet all thresholds. In the burst, every member ended with exactly one session (REQ-NF-42) and there were no errors, but the p95 is above the 3 second threshold. The likely cause is the PHP-FPM default of 5 workers on a laptop running Docker on Windows. \revised{The team will raise the worker count and repeat the test on the CTI server.} Repeating Check In for the same user returns the same session (idempotent). \revised{Location accuracy at the gym is measured for the Final report.}
